---
项目使用 Nix 进行环境管理，当你需要为项目配置或修改 Nix、devenv 相关内容时，请参考此说明
---

## 基本原则

- 使用 Nix 管理项目的软件包、构建依赖及开发环境
- 优先使用 Nixpkgs 中已有的软件包，避免重复实现
- 优先采用声明式配置，避免依赖开发者本机的隐式环境
- 确保依赖版本和构建输入具有可追溯性
- 尽可能保证不同开发环境和 CI 环境之间的一致性
- 保持 Nix 配置简洁，避免不必要的抽象和复杂的表达式
- 合理划分配置文件，避免将所有内容集中在单个文件中
- 优先使用稳定、维护活跃的软件包和依赖来源
- 不要为了使用 Nix 而重复管理其他工具已经负责的依赖

## 文件名称

Nix 配置文件应当根据实际用途选择合适的名称

项目使用 Flakes 时，统一使用以下文件：

- `flake.nix`：定义项目输入、依赖及输出
- `flake.lock`：锁定 Flakes 输入及其版本

当配置内容较多时，可以将 Nix 表达式拆分到 `nix` 目录中，并由 `flake.nix` 引用

例如：

```text
project/
├── flake.nix
├── flake.lock
├── nix/
│   ├── packages.nix
│   ├── shells.nix
│   └── overlays.nix
└── src/
```

不需要为了拆分而拆分，简单项目应优先保持配置集中

## Flakes

项目需要使用 Nix 管理依赖和构建输出时，优先考虑使用 Flakes

### inputs

`inputs` 用于声明项目依赖的其他 Flakes 或外部资源

- 明确声明项目所需的依赖
- 优先使用官方或可信来源
- 对重要依赖使用明确的分支、版本或引用
- 避免引入不必要的间接依赖
- 当多个依赖需要使用同一份 Nixpkgs 时，合理使用 `follows` 避免重复引入
- 不要在配置中使用来源不明的远程依赖

### outputs

`outputs` 用于定义项目向外提供的构建结果和开发环境

根据项目实际需求使用对应的输出：

- `packages` 软件包及构建产物
- `devShells` 开发环境
- `apps` 可执行应用
- `checks` 自动化检查及构建验证
- `overlays` 软件包覆盖配置
- `nixosModules` NixOS 模块（需要时）

不要为了满足某种固定结构而定义没有实际用途的输出

### lock 文件

- `flake.lock` 应当纳入 Git 版本控制
- 不要手动修改 `flake.lock`
- 使用 Nix 命令更新依赖锁定信息
- 依赖更新应当作为独立变更进行
- 更新后应检查构建结果和开发环境
- 不要在日常开发中无必要地更新全部依赖
- 不要在 CI 中自动修改并提交锁文件

Flakes 目前仍属于 Nix 的实验性功能，使用时应明确项目对 Nix 版本及相关功能的要求

## Nixpkgs 与软件包管理

使用 Nixpkgs 提供的软件包时，应遵循以下原则：

- 优先使用 Nixpkgs 中已有的软件包
- 使用 `pkgs` 作为软件包集合的统一入口
- 对重要的软件包明确选择合适的版本
- 不要无必要地直接引用软件包的内部属性
- 不要重复定义 Nixpkgs 已经提供的软件包
- 优先使用正式的软件包属性，不要依赖过时或已废弃的属性
- 引入软件包之前，应检查其维护状态、许可证及适用平台

对于项目所需的工具链，应根据实际需求选择合适的版本，不要默认使用系统中已经安装的软件

## 软件包定义（packages）

当项目需要通过 Nix 构建、分发自己的软件时，应使用标准的 Nix 构建方式定义软件包

- 优先使用 Nixpkgs 提供的构建函数
- 明确声明构建输入和运行时依赖
- 将构建过程限制在声明的依赖范围内
- 避免依赖构建机器上的全局软件和环境变量
- 正确处理构建、安装及检查阶段
- 合理使用构建缓存
- 尽可能保证构建过程的确定性和可复现性

对于已有的语言生态构建工具，应优先使用其成熟的构建方式，不要无必要地重新实现构建流程

## 开发环境（devShells）

使用 `devShells` 定义项目所需的开发环境

- 只声明项目实际需要的开发工具
- 对重要工具链明确指定版本
- 合理组织编译器、调试器、代码检查工具及其他辅助工具
- 避免引入与项目无关的软件包
- 不要将开发工具和生产运行时依赖混为一谈
- 进入开发环境时避免执行耗时或具有破坏性的操作

例如：

```nix
devShells = forAllSystems (system:
  let
    pkgs = import nixpkgs { inherit system; };
  in {
    default = pkgs.mkShell {
      packages = with pkgs; [
        git
        jq
      ];
    };
  }
);
```

进入开发环境：

```bash
nix develop
```

对于多个具有不同工具需求的开发场景，可以定义多个开发环境，例如：

- `default` 通用开发环境
- `ci` CI 专用环境
- `docs` 文档开发环境

不要为了少量工具差异创建过多开发环境

## 系统平台（Systems）

Nix 配置应当明确考虑目标系统平台

- 根据项目实际需求支持对应的操作系统和 CPU 架构
- 不要无必要地将平台限制为单一架构
- 对不同平台存在差异的依赖和构建过程，应明确处理
- 避免假设所有开发者都使用相同的操作系统
- 不支持的平台应当有明确的限制说明

常见平台包括：

- `x86_64-linux`
- `aarch64-linux`
- `x86_64-darwin`
- `aarch64-darwin`

不要仅为了形式上的跨平台支持而引入无法实际构建的配置

## 依赖管理

Nix 主要负责系统级软件包、工具链和构建依赖，不应无必要地替代各语言生态的依赖管理工具

| 生态    | 推荐工具       |
|---------|----------------|
| Python  | uv             |
| Node.js | pnpm           |
| Rust    | Cargo          |
| Go      | Go Modules     |
| Java    | Maven / Gradle |

- 使用 Nix 提供必要的语言运行时和开发工具
- 使用对应生态的工具管理项目依赖
- 不要在 Nix 和语言生态中重复管理同一层级的依赖
- 明确区分构建依赖、开发依赖和运行时依赖
- 对依赖版本使用对应工具的锁文件进行管理

## Overlays 与 Overrides

当需要修改或扩展 Nixpkgs 中的软件包时，可以使用 Overlays 或 Overrides

- 优先使用 Nixpkgs 已有的软件包配置
- 只有在现有软件包无法满足需求时才使用 Overrides
- 只有在需要扩展或统一修改软件包集合时才引入 Overlays
- 避免重复覆盖已经满足需求的软件包
- 明确覆盖操作的影响范围
- 不要为了修改单个项目的简单配置而引入复杂的 Overlay 体系

对于需要长期维护的自定义软件包，应考虑将其独立定义，避免与项目其他配置产生不必要的耦合

## 缓存与构建

合理使用 Nix Store 和 Binary Cache 减少重复构建

- 优先复用已有的构建结果
- 对适合缓存的构建输入保持稳定
- 避免频繁改变无关的构建输入
- CI 应合理配置缓存以减少重复下载和构建
- 不要将缓存作为依赖正确性的前提
- 不要在项目配置中引入来源不明的 Binary Cache
- 对第三方 Binary Cache 应评估其可信度和安全性

## 安全与环境变量

- 不要在 Nix 表达式中硬编码真实密钥、令牌及其他敏感信息
- 不要将敏感信息写入 `flake.nix`、`flake.lock` 或其他可能进入 Nix Store 的文件
- 不要假设 Nix Store 中的内容具有访问权限隔离
- 对需要使用敏感信息的操作，使用适当的密钥管理机制
- 避免在构建过程中访问未经声明的外部资源
- 对远程依赖和构建输入使用可信来源

## 与其他工具的协作

避免多个工具重复承担相同职责

### 与 devenv 的协作

[devenv](https://devenv.sh/) 是基于 Nix 的开发环境管理工具，可以用于简化项目开发环境的定义和管理

- 项目开发环境使用 devenv 配置，优先使用 devenv 提供的开发环境管理能力
- 不要在 `flake.nix` 和 `devenv.nix` 中重复定义相同的开发环境
- Nix 负责底层软件包和构建能力，devenv 负责更高层次的开发环境组织
- 对于 devenv 已经提供的服务模块，优先使用现有模块
- 对于 devenv 无法满足的特殊需求，可以直接使用 Nix 能力补充
- 不要为了使用 devenv 而引入不必要的 Flakes 集成或额外抽象

### 与 Taskfile 的协作

项目使用 Taskfile 作为任务运行的统一入口，参考[taskfile.md](./taskfile.md)

Nix 负责提供软件和运行环境，Taskfile 负责组织和执行项目工作流

- 不要在 Nix 中重复定义 Taskfile 已经管理的项目任务，任务主要由 Taskfile 管理
- 不要使用 Nix 构建脚本替代常规的项目自动化任务
- 对于需要 Nix 环境的任务，应确保执行时使用正确的开发环境
- 可以通过 `nix develop --command` 在开发环境中执行 Taskfile
- 不要在 Taskfile 和 Nix 中重复维护相同的软件包及版本配置

### 与 CI 的协作

CI 应尽可能使用与本地一致的 Nix 配置

- 优先复用项目已有的 `flake.nix` 和 `flake.lock`
- 使用 Nix 提供的环境执行检查、测试和构建
- 对适合的构建结果使用 Binary Cache
- 明确 CI 所使用的系统平台
- 避免在 CI 中重新维护已经由 Nix 管理的工具链版本
- 不要在 CI 中自动更新项目依赖锁文件
- 确保 CI 使用的 Nix 版本满足项目要求

## 维护与更新

- 定期检查 Nixpkgs 和其他 Flakes 输入的维护状态
- 根据项目需要更新依赖
- 更新后执行必要的构建和检查
- 清理不再使用的软件包定义和配置
- 对复杂的 Nix 表达式提供必要的说明
- 避免引入无法解释用途的配置和依赖
